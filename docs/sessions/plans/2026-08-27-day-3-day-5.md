## Working method

### TDD/BDD cycle

For every behavior:

1. write the failing domain or contract scenario with its requirement ID;
2. implement the smallest domain behavior;
3. add trusted Function and persistence adapters;
4. prove negative scope, retry, failure, and cleanup paths;
5. add the FR/EN UI and browser scenario;
6. deploy Preview and collect non-sensitive evidence;
7. refactor only while all gates remain green.

SOLID boundaries remain explicit: domain policy does not depend on Appwrite,
React, GitHub, GitLab, SMTP, IndexedDB, or telemetry implementations. Provider
and persistence details implement narrow ports owned by the use case.

### Git and PR strategy

- Use one short-lived branch per task or tightly coupled vertical slice, for
  example `task/TASK-ADMIN-001-administration`. Start every branch from the
  latest validated `main`.
- Produce atomic commits inside each task branch; every commit must leave the
  branch buildable and include the tests required by its behavior.
- Use one reviewable PR per task or tightly coupled vertical slice. A gate is
  an integration checkpoint over merged task PRs, not a branch containing
  unrelated Day work. High-risk migrations or provider deployments remain
  independently revertible.
- Rebase before review and merge by rebase after required checks pass.
- Author all commits as `Y4NN777 <axel.studiesmail@gmail.com>` and sign them
  when the repository rule requires it.
- Never commit `.env.*`, provider tokens, Appwrite keys, Access Proofs, HMAC
  authorities, private identifiers, captured emails, or raw provider payloads.

Atomic commit examples:

```text
feat(admin): enforce project administration policies
feat(conversation): separate messages from internal notes
feat(lifecycle): implement attributable feedback transitions
feat(workbench): add scoped maintainer feedback workspace
feat(notifications): deliver scoped feed and email events
feat(sources): complete repository import and badge flow
feat(issues): enforce consent-aware issue linking
feat(offline): add partitioned durable client outbox
feat(sync): reconcile provider lifecycle and messages
feat(intelligence): add scoped trends and provenance
feat(privacy): implement deletion restore and purge
feat(platform): enforce independent exceptional access
test(release): prove full-system recovery and rollback
```

### Standard local quality gate

Run after every atomic slice and before each task PR and gate checkpoint:

```bash
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm test:coverage
pnpm build
pnpm test:e2e
pnpm security:scan
```

Every new real-service verifier must be added as a named `pnpm verify:*`
command and to CI where it can run without long-lived secrets.

### D3.1 — `TASK-ADMIN-001`

Build:

- domain commands for Project creation/update, type/Context configuration,
  slug change/history, activation/deactivation, Maintainer assignment/removal;
- trusted Function endpoints deriving Workspace/Project scope from the actor;
- transactional Appwrite adapters and first-party FR/EN administration UI;
- immutable audit facts for every accepted administration action.

Red/green scenarios:

- Owner succeeds; Maintainer and unassigned principal fail without disclosure;
- slug collision and reuse fail; invalid Context/type/activation leaves state
  unchanged; removal ends access immediately;
- request retry produces one fact and one audit event;
- direct Appwrite access cannot bypass the Function.

Definition of Ready:

- trace: `UC-07`, `FR-OPS-002..004`, `FR-OPS-010`, `NFR-EVO-001`,
  `NFR-EVO-003`, and `NFR-EVO-005`;
- actor and scope: a verified Workspace Owner manages only the authoritative
  Workspace derived from active membership; Maintainers, unassigned actors,
  forged principals, sibling Workspaces and revoked sessions receive the same
  non-disclosing denial;
- authorization order: parse the command, verify the Appwrite JWT, resolve the
  active Workspace membership, authorize Owner capability, then read or mutate
  Project state. Project creation and inactive-Project reactivation must not
  depend on a resolver that requires an already-active Project;
- trust boundary: React sends commands only to the trusted Function. The
  Function owns scope derivation, validation, idempotency, transaction commit,
  audit creation and response redaction;
- prohibited data: JWTs, credentials, provider grants, Reporter identity,
  Access Proofs, private Feedback content and raw SDK errors never enter audit,
  logs, analytics, URLs or client persistence;
- deterministic dependencies: inject command ID, row ID, clock and payload
  digest; real Preview evidence uses two Workspaces, two Projects, Owner,
  Maintainer, unassigned and revoked principals.

Behavior matrix:

| Scenario | Given | When | Then |
| --- | --- | --- | --- |
| `BDD-ADMIN-001` | an active Owner membership and an unused Project ID/slug | the Owner creates a valid Project | Project, current slug, idempotency result and one immutable audit fact commit atomically |
| `BDD-ADMIN-002` | Maintainer, unassigned, forged, revoked or cross-Workspace authority | the actor submits any administration command | the same non-disclosing denial is returned and no Project data is read or changed |
| `BDD-ADMIN-003` | an existing Project | the Owner configures valid enabled types, declared Context and FR/EN purpose | the complete validated configuration changes once and the public projection reflects it |
| `BDD-ADMIN-004` | invalid, executable, duplicate or oversized type/Context configuration | the Owner requests an update | configuration, idempotency and audit remain unchanged |
| `BDD-ADMIN-005` | a current or historical reserved slug | the Owner creates or renames another Project to it | the collision is rejected and both Projects remain unchanged |
| `BDD-ADMIN-006` | an existing Project and a new globally unused slug | the Owner renames it | the new slug becomes canonical and every prior slug remains a permanent redirect |
| `BDD-ADMIN-007` | an active or inactive Project | the Owner changes activation | exactly one state change and audit fact commit; an invalid/no-op transition changes nothing |
| `BDD-ADMIN-008` | an active Maintainer membership | the Owner assigns then removes the Maintainer | assignment grants only that Project and removal denies the next protected request immediately |
| `BDD-ADMIN-009` | a completed administration command | the client retries the same operation ID and payload after response loss | the original result is returned with no duplicate state or audit fact |
| `BDD-ADMIN-010` | a completed operation ID | the client reuses it with a different payload | a stable conflict is returned and all authoritative state remains unchanged |
| `BDD-ADMIN-011` | a forced failure before every transactional write and commit | the command executes | the transaction rolls back and exposes only a retryable non-sensitive outcome |
| `BDD-ADMIN-012` | no browser table/storage permission | a client attempts direct Appwrite mutation | Appwrite denies it and the Function remains the only product administration path |

Architecture decision:

- retain normalized authoritative state in the existing Projects, permanent
  slug reservations and Project assignments tables;
- add capability-focused administration command/orchestration ports plus
  separate append-only administration audit and idempotency tables;
- commit current state, slug/assignment change, idempotency result and audit
  fact in one Appwrite transaction. Do not introduce event sourcing, an
  asynchronous projection or a generic JSON repository for this slice;
- expose explicit command/result unions and stable `ERR-ADMIN-*` transport
  mappings; no adapter or SDK type enters the domain package.

Migration and rollback contract:

1. add the two private tables and their required indexes through a versioned,
   additive manifest; do not alter existing data during provisioning;
2. prove plan/replay/drift behavior locally before applying Preview;
3. deploy code that tolerates the new empty tables before enabling the
   administration routes;
4. rollback code first. Remove newly created tables only before real commands
   exist; after accepted audit/idempotency facts exist, rollback is
   forward-compatible and non-destructive;
5. force a provisioning failure before apply and after each created resource,
   then prove deterministic resume without duplicate or partially enabled
   administration behavior.

Evidence command to add: `pnpm verify:appwrite:g3:admin`.
